Google Cloud Identity vs. Workforce Identity Federation (WIF)

Selecting between Cloud Identity and Workforce Identity Federation is the most fundamental security & governance decision in your Google Cloud foundation. Review the core architectural trade-offs below, use our interactive advisor, or jump straight to Step 1 to choose your model.

Why Choose Workforce Identity Federation (WIF)

Workforce Identity Federation lets enterprise workers use an external Identity Provider (Entra ID, Okta, Ping) to authenticate to Google Cloud without creating managed Google accounts.

Zero User & Group Synchronization: No users or credentials stored in Google. SCIM 2.0 and GCDS sync tools are completely bypassed.
100% Free - Zero Google User Licenses: Built into Google Cloud IAM. Eliminates Cloud Identity Free/Premium licensing constraints.
Direct Protocol Flexibility (SAML 2.0 & OIDC): Supports both SAML and OpenID Connect with standard discovery.
Dynamic Group RBAC: Maps IdP group claims straight to IAM roles (principalSet://.../group/...) without creating Google Groups.
Best For: Developers, DevOps, Cloud Engineers, external contractors, and multi-cloud teams accessing GCP Console, CLI, and APIs.
Managed Accounts • Directory Sync Workspace Ready

Why Choose Google Cloud Identity (Managed Accounts)

Google Cloud Identity provisions and mirrors physical Google user accounts (user@company.com) into the Google Admin Console, authenticating via third-party SAML SSO.

Google Workspace Ready (Mandatory): Essential if users need Gmail, Google Drive, Docs, Sheets, Calendar, or Google Meet integration.
Mobile Device Management (MDM) & Chrome: Enforces Google Endpoint Management for Android/iOS BYOD and company devices, plus Chrome Enterprise browser policies.
Automated Directory Provisioning: Synchronizes user accounts and groups from Entra ID (SCIM), Okta (OIN Push Groups), Ping, or Active Directory (GCDS).
Centralized Google Groups: Synchronized groups can be granted GCP IAM roles (group:ops@company.com) and document sharing permissions.
Best For: Enterprise knowledge workers, employees needing Google collaboration tools, and organizations using Google MDM.
Hybrid Coexistence Model (Best of Both Worlds)

You do not have to choose only one! Large enterprise organizations routinely use Cloud Identity for corporate employees who need Google Workspace or mobile endpoint management, alongside Workforce Identity Federation for external contractors, developers, and partner engineering teams accessing GCP projects without creating Google accounts or paying user licenses.

Infrastructure as Code & CLI Generator

Copy ready-to-execute `gcloud` commands or complete Terraform HCL modules customized with your workspace parameters.

Authoritative References: gcloud CLI Reference ↗ Terraform google_iam_workforce_pool ↗ Terraform google_iam_workforce_pool_provider ↗
1. Create Workforce Identity Pool 
# Run in Cloud Shell or local gcloud CLI
gcloud iam workforce-pools create enterprise-corp-pool \
    --organization="102938475601" \
    --location="global" \
    --display-name="Enterprise Workforce Identity Pool" \
    --description="Federated access pool for external enterprise IdP"
2. Create SAML / OIDC Workforce Provider 
gcloud iam workforce-pools providers create-saml primary-idp \
    --workforce-pool="enterprise-corp-pool" \
    --location="global" \
    --display-name="Entra ID SAML Provider" \
    --idp-metadata-xml-path="metadata.xml" \
    --attribute-mapping="google.subject=assertion.subject,google.groups=assertion.attributes.groups,attribute.department=assertion.attributes.department" \
    --attribute-condition="assertion.attributes.groups.contains('gcp-engineers')"
3. Grant IAM Role to Federated Principal Set (e.g. Group) 
gcloud projects add-iam-policy-binding acme-cloud-sec-prod \
    --role="roles/viewer" \
    --member="principalSet://iam.googleapis.com/locations/global/workforcePools/enterprise-corp-pool/group/gcp-engineers"
4. Generate gcloud CLI Client Credential Configuration 
# Generate credential configuration for developers to use gcloud CLI without a Google Account
gcloud iam workforce-pools create-cred-config \
    locations/global/workforcePools/enterprise-corp-pool/providers/primary-idp \
    --output-file=workforce-config.json

# User authenticates with their corporate IdP credentials in browser
gcloud auth login --cred-file=workforce-config.json

# Google Workforce Identity Federation Terraform Module
resource "google_iam_workforce_pool" "pool" {
  workforce_pool_id = "enterprise-corp-pool"
  parent            = "organizations/102938475601"
  location          = "global"
  display_name      = "Enterprise Workforce Pool"
  description       = "Automated enterprise workforce pool"
}

resource "google_iam_workforce_pool_provider" "provider" {
  workforce_pool_id = google_iam_workforce_pool.pool.workforce_pool_id
  location          = "global"
  provider_id       = "primary-idp"
  display_name      = "Corporate IdP"

  attribute_mapping = {
    "google.subject"       = "assertion.subject"
    "google.groups"        = "assertion.attributes.groups"
    "attribute.department" = "assertion.attributes.department"
  }

  saml {
    idp_metadata_xml = file("${path.module}/metadata.xml")
  }
}

# Grant role to federated group
resource "google_project_iam_member" "workforce_group_binding" {
  project = "acme-cloud-sec-prod"
  role    = "roles/viewer"
  member  = "principalSet://iam.googleapis.com/${google_iam_workforce_pool.pool.name}/group/gcp-engineers"
}
Field Triage Playbook

Troubleshooting & Implementation Gotchas

Battle-tested solutions for the most frequent authentication, claim mapping, and provisioning failures.

Microsoft Entra ID emits Group GUIDs (Object IDs) instead of Group Names

Symptom: User logs in, but IAM permissions assigned to group display name (e.g. `gcp-engineers`) do not take effect.

Root Cause: By default in SAML and OIDC, Entra ID includes security group IDs as 36-character GUIDs (`7d21c4...`) to protect privacy and avoid naming collisions. Therefore, `assertion.attributes.groups` contains GUIDs, not `gcp-engineers`.

Solution 1 (Recommended): Bind IAM directly to the Entra Group Object ID:
--member="principalSet://iam.googleapis.com/.../group/7d21c430-8d5f-41ba-..."

Solution 2: In Entra ID Enterprise App > Token Configuration / Single sign-on, change the Group Claim format from "Security groups" to use sAMAccountName (for hybrid synced groups) or define custom App Roles where the role value is the human-readable group name.

OIDC Issuer URL Mismatch: `Invalid Issuer URI` or 400 Bad Request

Symptom: GCP Workforce Pool provider fails verification during token exchange.

Root Cause: Google Cloud STS strictly matches the iss claim in the JSON Web Token. In Microsoft Entra ID:

  • v1 token issuer: https://sts.windows.net/{tenant-id}/ (ends with trailing slash!)
  • v2 token issuer: https://login.microsoftonline.com/{tenant-id}/v2.0 (no trailing slash!)

Fix: Inspect a decoded token on jwt.ms. Copy the exact character-for-character value of the iss claim into the GCP Workforce Provider Issuer URL field.

SAML Signature Verification Failed / `Missing or Invalid X.509 Certificate`

Symptom: Sign-in callback fails with `INVALID_ARGUMENT: SAML signature is invalid`.

Root Cause: IdP signing option must be set to Sign SAML response and assertion or Sign SAML assertion. If only the response is signed or the certificate expired, GCP rejects the payload.

Fix in Okta: Advanced Sign-on Settings > Signature Algorithm: RSA-SHA256. Digest Algorithm: SHA256. Assertion Signature: Signed.

Fix in Entra ID: Single sign-on > SAML Signing Certificate > Signing Option > Select Sign SAML response and assertion.

SCIM Automatic Provisioning Quarantine / `401 Unauthorized`

Symptom: Entra ID or Okta stops syncing users into Cloud Identity with quarantine status.

Root Cause: The OAuth bearer token or admin service account credentials configured in the IdP provisioning tab have expired, or the Super Admin account who authorized the integration was de-provisioned.

Fix: In Okta or Entra ID Provisioning > Admin Credentials > Re-authenticate using a dedicated service Super Admin account that has a permanent non-expiring password or MFA bypass.
